# Engine Upgrade Audit

This document started as the Phase 0 repository audit and was refreshed during
Phase 7 to describe the current portfolio-ready renderer state. It is a status
document, not a roadmap for adding new rendering features.

## Current Repository Shape

- `src/core/` owns application startup, SDL3 window creation, event polling, PNG
  screenshot writing, logging, and the main loop.
- `src/rhi/` owns Vulkan instance/device/swapchain/resource wrappers,
  Synchronization2 helpers, debug labels, timestamp queries, VMA-backed buffers
  and images, texture upload, shadow maps, environment maps, and BRDF LUTs.
- `src/renderer/` owns frame orchestration, render objects, draw-item
  construction, material state, bindless texture heap, runtime settings, GPU
  profiler integration, scene JSON save/load, and Render Graph metadata.
  `Renderer` itself is one class spread across several translation units --
  `Renderer.cpp` (lifecycle, frame loop, input, settings), `RendererResources.cpp`
  (pipelines, descriptors, buffers, IBL), `RendererScene.cpp` (scene, materials,
  asset JSON), `RendererFrame.cpp` (per-frame CPU prep), `RendererRecord.cpp`
  (command recording), and `RendererDebugUi.cpp` (ImGui panels). Shared
  file-local helpers live in `RendererInternal.h`. The class is still large; only
  the file was split.
- `src/assets/` owns the path-based `AssetManager` for material JSON assets and
  texture path metadata. Runtime Vulkan images still live in renderer/RHI code.
- `src/ui/` owns Dear ImGui integration through `ImGuiLayer`.
- `src/shaders/` contains all GLSL sources compiled by CMake with `glslc`.
- `assets/` contains the committed test glTF, fallback textures, portfolio
  material JSON files, and intentionally small runtime assets.
- `config/` contains the tracked runtime settings example. User-local
  `config/runtime_settings.json` is generated by the UI and ignored by git.
- `screenshots/` contains finalized portfolio captures. Phase 7 does not modify
  those files.
- `tests/` contains the Catch2 suite CI runs headlessly. It links
  `VulkanEngineRuntime`, the static library the executable also links, which is
  what makes renderer-side code testable without a GPU.
- `tools/` contains the offline cooks (`vecook` for BC7 textures, `vemeshcook`
  for `.vemesh` geometry), the `compare_images` pixel differ the CI gate uses,
  and the measurement harness under `tools/dev/`.
- `config/ci/` contains one settings delta per configuration the headless job
  sweeps; each file states only what it changes from the defaults.

## Build And Runtime Entry Points

The root `CMakeLists.txt` defines the C++20 `VulkanEngine` executable and the
`VulkanEngineShaders` target, alongside the `VulkanEngineCore` and
`VulkanEngineRuntime` static libraries, the `compare_images` differ, and the
`vecook` and `vemeshcook` asset cooks. It first tries installed packages, then
can fetch SDL3, GLM, Volk, and Vulkan Memory Allocator from pinned tags when
`VULKAN_ENGINE_FETCH_DEPS=ON`. The Vulkan SDK is required for headers and
`glslc`.

`VULKAN_ENGINE_BUILD_TESTS` is on by default; `VULKAN_ENGINE_ENABLE_SANITIZERS`
and `VULKAN_ENGINE_WARNINGS_AS_ERRORS` are switches CI turns on rather than
defaults; and `VULKAN_ENGINE_FETCH_SAMPLE_SCENE` fetches the Sponza scene
`--scene sponza` needs.

CMake embeds these source/build paths into the executable:

- `VULKAN_ENGINE_SHADER_DIR`
- `VULKAN_ENGINE_ASSET_DIR`
- `VULKAN_ENGINE_CONFIG_DIR`

`src/main.cpp` constructs `ve::Application`, which creates `Window` and
`Renderer`, forwards SDL events, and calls `Renderer::drawFrame()` until exit.

## Implemented Renderer Scope

The current project is a C++20 Vulkan 1.3 real-time renderer prototype. It is
not a full game engine. Implemented systems include:

- Vulkan 1.3 device setup with Dynamic Rendering, Synchronization2, Volk, VMA,
  SDL3, optional validation, debug labels, and RAII-style resource wrappers.
- Static and skinned mesh rendering: built-in geometry, glTF static meshes, and
  GPU linear-blend skinning from a per-frame joint palette. Discrete LOD chains
  are built at load time and selected per draw item inside the cull dispatch.
- glTF import of material factors, base-color/normal/metallic-roughness/emissive
  textures, `MASK` and `BLEND` alpha modes, and skinned animation. Both halves
  of load cost have an optional cooked sidecar: `.vemesh` for geometry, BC7
  `.ktx2` for textures.
- PBR shading with Cook-Torrance GGX direct lighting, tangent-space normal
  maps, Kulla-Conty-style multi-scattering compensation, IBL, GGX prefiltered
  specular environment maps, and a split-sum BRDF LUT.
- Clustered (Forward+) lighting on a 32x18x24 froxel grid, with the cluster
  build and light cull on a dedicated compute queue where the device exposes
  one.
- Three shadow paths: PCF-filtered cascaded shadow maps with texel snapping and
  per-cascade content caching, a quadtree-packed punctual atlas with per-tile
  caching, and optional virtual shadow maps behind their own stage gates.
  Alpha-tested casters and a shadow LOD bias apply to the cascades.
- Indirect lighting beyond IBL, all optional: irradiance-probe GI, screen-space
  reflections against the thin G-buffer, GTAO, and volumetric fog.
- A depth prepass (on by default), GPU frustum culling, two-phase Hi-Z occlusion
  culling, indirect drawing, and culling debug counters.
- HDR scene color, mip-chain bloom by default, legacy blur fallback, histogram
  auto-exposure with a parallel reduce, Reinhard/ACES tone mapping, and
  motion-vector TAA whose resolve doubles as the temporal upsampler. Render
  scale and dynamic resolution render into a sub-rect of full-size targets, so a
  scale change reallocates nothing.
- Render graph with logical handles, pass read/write declarations, conservative
  barrier inference, pass liveness, an execution order derived from the declared
  dependencies, a backstop comparing declared passes against recorded ones, and
  optional transient memory aliasing of the bloom chain and the
  velocity/thin-G-buffer pair.
- Per-pass GPU timestamp profiling with frame-latency readback, seventeen CPU
  frame-preparation scopes, and ImGui timing history.
- Editable runtime scene workflow for object names, visibility, transforms,
  click-to-pick with a transform gizmo, camera/light settings, JSON scene
  save/load, and material asset path metadata.
- JSON material asset loading/saving for scalar PBR fields and path metadata.
- Overlay-free portfolio screenshot capture from the tonemapped swapchain image
  before ImGui, plus the scripted `--capture-frame` path the headless CI gate
  compares against a golden image.

## Frame Flow

The current frame flow is:

1. After the frame-slot fence signals, read back the completed frame's exposure,
   culling counters, timestamps, and any requested screenshot copy.
2. Acquire a swapchain image, reset the command buffer, build ImGui data, and
   run CPU frame preparation on the `JobSystem`: object transforms and world
   bounds, draw items, culling inputs, cascade and punctual shadow inputs, and
   `ObjectFrameData`.
3. Begin the render graph: import the swapchain, depth, shadow, TAA and
   depth-pyramid resources, declare the transient scene, bloom, SSR, GTAO and
   fog resources, and declare this frame's passes. Which passes are declared
   depends on what is enabled and on what the caches decided -- a frame whose
   cascades are all clean declares no `CSMShadowPass`.
4. `RenderGraph::recordScheduledUnits` drives the rest as seventeen recorders,
   in the order the graph scheduled them:
   - virtual shadow map page marking, page cull, and page render;
   - cascaded shadow maps, with an optional GPU caster cull ahead of them;
   - the punctual shadow atlas, with an optional GPU cull ahead of it;
   - main GPU frustum and Hi-Z culling against the previous frame's pyramid;
   - cluster build and light cull, on the async compute queue when the device
     exposes one and on the graphics queue here when it does not;
   - volumetric fog injection and integration;
   - irradiance probe capture and convolution;
   - the main geometry region: depth prepass, then skybox and opaque draws into
     `SceneColorHDR` alongside the velocity and thin G-buffer attachments, the
     phase-two occlusion re-test, SSR, GTAO, and the transparent pass;
   - the depth pyramid build the next frame's culling reads;
   - TAA resolve, which reconstructs at presentation resolution;
   - bloom (mip chain or legacy), luminance, histogram exposure, and composite;
   - screenshot copies when requested, then the ImGui overlay.
5. `RenderGraph::endFrame` compares the passes that were begun against the ones
   that were declared, and reports order violations, unrecorded passes, and
   declaration issues.
6. Transition the swapchain image to present, submit with `vkQueueSubmit2`, and
   present.

## Current Render Graph

`renderer::RenderGraph` is still a compact renderer-owned graph, not a full
production scheduler. What has changed is coverage: it declares the whole frame
rather than its tail, and the order it schedules is the order the frame records.
In declaration order it can declare:

`VsmPageMarkPass`, `VsmPagePass`, `ShadowGpuCullingPass`, `CSMShadowPass`,
`PunctualShadowCullPass`, `PunctualShadowAtlasPass`, `MainGpuCullingPass`,
`VolumetricFogPass`, `ProbeCapture`, `IrradianceProbeUpdate`, `DepthPrepass`,
`MainHDRPass`, `DepthPyramidMidPass`, `MainGpuCullingPhase2`, `MainHDRPhase2`,
`SSRCopyPass`, `SSRTracePass`, `GTAOPass`, `GTAOBlurPass`, `TransparentPass`,
`DepthPyramidPass`, `TAAResolvePass`, the legacy bloom extract and blur passes,
the mip-chain bloom downsample and upsample chains, `LuminancePass`,
`HistogramExposurePass`, `CompositePass`, and `ImGuiPass`.

Most of those are conditional, and the condition is the interesting part. A pass
declared on a frame that never records it leaves the graph's barriers, liveness
and resource lifetimes describing work that did not happen, and no validation
error is raised because each individual Vulkan call is still legal.
`RenderGraph::endFrame` is what catches that, and the headless job renders
[every configuration in its sweep](../config/ci/README.md) past it, with a check
that fails when a path-selecting setting is left out of the sweep.

It tracks logical texture and buffer handles, imported and transient resource
metadata, declared access, conservative image transitions and buffer barriers,
side effects, pass liveness, execution order, and debug UI rows. Physical
resource allocation remains in `Renderer`.

Manual barriers remain where they sit inside one pass rather than between two:
the depth pyramid's per-mip chain, the fog's injection-to-integration edge and
its one-time clear, each cull's reset, readback copy and host-visibility
barrier, and the portfolio screenshot copy, which transitions the swapchain
image between `CompositePass` and `ImGuiPass` and back. Two pass-boundary edges
are not converted yet -- the VSM page cull and the probe shading parameter
buffer -- and [render_graph.md](render_graph.md) records what each needs first.

## Scene, Mesh, Material, And Assets

Current renderer-side scene data is deliberately small:

- `Camera` stores position, target, up vector, FOV, and near/far planes.
- `Transform` stores position/rotation/scale or a matrix override.
- `RenderObject` stores a stable runtime/editor ID, debug ID, name, visibility,
  mesh/material pointers, optional glTF material table, source type, transform,
  and portfolio/debug flags.
- `Mesh` owns GPU-local vertex/index buffers, submesh primitive ranges, a flat
  LOD table the cull dispatch selects from, meshlet ranges when a run asks for
  them, local bounds, and debug names. A cooked `.vemesh` sidecar beside the
  glTF skips assembly and LOD construction at load.
- `Material` stores runtime texture pointers, descriptor state, bindless
  indices, PBR factors, alpha metadata, source asset path, source type, and
  fallback flags.
- `AssetManager` provides stable path-derived material/texture handles and
  material JSON load/save, but it does not own Vulkan GPU resources.

Scene JSON is intentionally narrow. It restores matching runtime objects,
camera/light settings, object names, visibility, transforms, and simple material
asset assignments when the material already exists in the runtime scene. It does
not create objects, rebuild mesh assets, rebuild glTF material tables, or act as
a full editor scene format.

## Debug UI And Portfolio Workflow

Dear ImGui exposes renderer controls and inspection panels for:

- runtime settings save/load/reset
- tone mapping, exposure, bloom, and TAA controls
- CSM controls
- GPU culling and occlusion settings/counters
- portfolio capture mode and screenshot status
- Render Graph pass/resource tables
- GPU profiler timing history
- scene hierarchy editing and camera/light controls
- material scalar editing, save, and reload
- texture, render-target, TAA history, depth-pyramid, and CSM previews
- per-subsystem panels for SSR, GTAO, volumetric fog, irradiance probes,
  virtual shadow maps, punctual shadows, mesh LOD, render scale and dynamic
  resolution, skeletal animation, and the scene presets

Portfolio capture mode is a runtime preset for presentation screenshots. It is
not an offline renderer, and F12 should only be used when intentionally updating
screenshots.

## Accurate Limitations

- No full game engine, physics, gameplay scripting, full ECS, production editor,
  asset browser, material graph, or texture import pipeline.
- The render graph does not schedule across queues. Async compute exists, but
  the renderer owns that submission rather than the graph (see
  async_compute.md). Memory aliasing covers the bloom chain and the
  velocity/thin-G-buffer pair and is off by default, measured as not worth its
  frame cost here, and transient resources are graph-described but still
  physically allocated by `Renderer`.
- Every shadow path caches: the punctual atlas per tile, the cascades per
  cascade and the virtual shadow map per page, each redrawing only when what it
  holds moved. The
  cascade cache is a static-scene win and, as measured, nothing else: the
  cascades are fitted to the camera, so any camera motion dirties all of them.
  The optional bounding-sphere fit does not change that -- it makes the ortho
  extent rotation-invariant, but the slice centre still orbits the camera, and
  the matrix survives only 0.0025-0.041 degrees of yaw. Making cascades cacheable
  under a moving camera needs the cascade anchored to the camera position rather
  than to the frustum slice, which is a different and lossier trade and is not
  implemented.
- Occlusion culling is conservative and AABB based, on by default. Phase 1 uses
  the previous frame's depth pyramid; phase 2 re-tests its rejects against a
  mid-frame rebuild, so disocclusions are rescued in the same frame rather than
  popping in the next one.
- TAA reprojects along a real velocity buffer, and its resolve doubles as the
  temporal upsampler, reconstructing at presentation resolution from the
  jittered low-resolution samples. It has no depth-based disocclusion
  classification, no reactive masks and no broad camera-cut detection.
  Skinned meshes carry joint-space motion through a previous-frame palette.
- Reflections are environment IBL plus screen-space reflections. There is no ray
  tracing, planar reflection, local reflection probe, or glass
  transmission/refraction, and SSR only finds what is on screen.
- glTF support is narrow but no longer static: skinned meshes with skeletal
  animation import, and `MASK`/`BLEND` alpha modes drive real cutout and
  transparent passes. Still unsupported: morph targets, cameras, lights, and
  occlusion maps. Emissive factor + emissive maps are supported.
- Upload paths still use one-time command buffers and queue-idle waits for
  initialization, and are not a runtime streaming system. Texture uploads are
  batched behind a bounded staging budget and take a dedicated transfer queue
  where the device exposes one, but nothing overlaps the copies with the rest
  of loading (see asset_system.md).
- GPU profiler timestamps are useful pass-duration estimates, not CPU/GPU
  calibrated timeline events.
- Portfolio screenshots use the current swapchain resolution rather than a
  separate high-resolution offline render path.

## Keeping this current

This file is linked from the README three times, including as the full list of
current limitations, so a stale claim here contradicts the feature table on the
front page. It fell behind once already: it still described the engine as having
