实测笔记 / GPU-Driven Rendering

被 LOD 吃掉的 Meshlet

我给一个 Vulkan 渲染器加了 meshlet 剔除的全部前置设施，然后在写 GPU pass 之前先量了一次。 它能省下 0.055% 的三角形。这篇讲为什么——以及那个数字其实挺有意思。

Vulkan 1.3 · RTX 3080 Ti Laptop · 锁频 1402/7001 · 每个场景 400 帧确定性回放

01 / 出发点

为什么想做这件事

对一个已经是 GPU-driven 的渲染器来说，meshlet 剔除几乎是默认的下一步：视锥剔除和两阶段 Hi-Z 遮挡剔除都已经在 compute 里按对象粒度跑了， 再往细一层走就是把网格切成 64 顶点 / 124 三角形的簇，每簇带一个包围球和一个法线锥，逐簇拒绝。 这也是图形岗面试里最常被追问的一环。

我的引擎里已经有 meshoptimizer（它在建 LOD 链），所以 meshopt_buildMeshlets 是零新依赖。 设施部分做完了：meshlet 被建成现有索引缓冲里的连续区间—— meshopt 原生吐的是 meshlet 局部的顶点表和微索引表，那需要第二个索引缓冲或者 mesh shader 才能画； 改成重排每个 LOD 级内部的三角形之后，一个 meshlet 就是一对 (firstIndex, indexCount)， 和 LOD 级的寻址方式完全一致，幸存的 meshlet 直接变成一条普通的 VkDrawIndexedIndirectCommand，绘制路径一行都不用改。

然后我停下来，先量了一次。

02 / 方法

在写 GPU pass 之前先量

meshlet 剔除值不值得，完全取决于内容。而我的场景全是程序化生成的——立方体和球体。 先把 GPU pass、per-meshlet 的 command 预算、计数器回读全写完再来测，等于赌一个我还没验证的前提。

所以我加了一个 CPU 侧的分析开关 --meshlet-analysis：它跑一遍 GPU pass 会 跑的那套剔除， 但什么都不改变，只汇报。有一个细节是必须的——先做对象级视锥测试，再统计 meshlet。 meshlet 剔除只会作用在既有 pass 已经保留下来的对象上，把被对象级剔除掉的那些也算进"节省"里， 省下的是本来就没人会做的工作。

03 / 结果

六个场景，400 帧确定性回放

场景 draw item meshlet 移除的三角形 indirect command
stress 1334 3323 0.055% 1334 → 3321
default 11 100 19.0% 11 → 82
sunlit 8 34 8.5% 8 → 32
occlusion 126 126 0% 不变
fragment-stress 9 9 0% 不变
cornell 7 7 0% 不变

唯一一个几何量值得剔除的场景是 stress。在那里 meshlet 剔除移除 0.055% 的三角形， 同时把 indirect command 数量乘了 2.5 倍。 那几个显示两位数百分比的场景，draw item 只有个位数——绝对值是几千个三角形。

04 / 解释

为什么这么少：LOD 已经拿走了

第一反应当然是 meshlet 建得不好。不是。把同一场景、同一机位的每个 draw item 强制到 level 0：

LOD 移除 87.1% 1,471,956 → 190,377 个三角形，一次 selectLodIndex，在一个本来就存在的 dispatch 里。
meshlet 再移除 0.055% 在 LOD 之后的剩余里。需要第二级剔除、独立的 command 预算和计数器回读。
关掉 LOD 时 23.5% 锥体剔除是有效的——只要它面前还有稠密几何。

这就是全部答案：LOD 选级和 meshlet 锥体剔除在抢同一份收益，而 LOD 先到一步。 在同样的剩余量上，LOD 的效率是 meshlet 的 7.7 倍，而且它不需要任何新东西。

还有一层更安静的原因。在这些内容实际选到的 LOD 级上，一整个球已经只剩下屈指可数的几个 meshlet， 每个 meshlet 因此覆盖了对象的大半个表面，法线朝向散得太开—— meshopt 给回来的 cone_cutoff 直接就是 1，也就是"永不拒绝"这个哨兵值。

meshlet 剔除想要的是又大、又近、又稠密的对象上的许多小簇。 而 LOD 的全部工作，就是保证这样的对象永远不会被提交。

05 / 成本的另一半

不是只有收益需要量

三角形百分比不能单独决定这件事。每个幸存的 meshlet 都是一条 indirect command， 而它替代的是原本的一个 draw item。stress 上是 1334 → 3321，2.5 倍。

如果关掉 LOD 让 meshlet 剔除去发挥那 23.5%，command 数会变成 13,931—— 而我的 kMaxDrawItems 是 8192。也就是说走这条路要先动容量上限， 而且按照这个引擎既有的约定，超出上限的几何必须被计数上报，而不是静默丢弃。

06 / 边界

什么情况下这个结论会反转

有大块连续网格、而且离相机很近的内容。Sponza 是最典型的那个： 一面墙横跨整个屏幕，LOD 拿它没办法——它不是"远处的小物件"，降级会直接看出来。 那种情况下 LOD 之后的剩余量远不止 0.055%。

所以我没有把这套设施删掉。buildMeshlets、 锥体测试和 --meshlet-analysis 都留在主干上（有单元测试，包括"meshletize 是每个 LOD 级内部三角形的一个置换"这条不变量）。 换内容重测是加一个命令行开关的事，不是重写一遍。

默认是关的，而且只能在启动时开。原因不是性能，是那个三角形重排： 它是三角形的置换，但不是光栅化顺序的置换——在默认场景上它会让 7.45% 的像素发生变化（最大通道差 6/255）， 来自深度打架的胜负判定和跟在后面的自动曝光反馈。那是一次 golden 图重烘， 而为了没有任何 shader 会读的数据去付这个代价，是本末倒置。

附录 / 一个差点骗过我的测量陷阱

不存在的那个 10.7% 回退

顺带说一个在这次测量里踩到的坑，因为它会坑掉任何一个"拿两个二进制做 A/B"的人。

我一度想把 meshlet 区间塞进 MeshLod 结构体里（8 字节 → 16 字节）。 量下来：帧时间 +10.7%，对照组漂移 0.43%，可复现，定位到 RenderObjects +31.9%。 看起来铁证如山。

它是假的。build/<config>/shaders/*.spv 是共享的。 我把 VulkanEngine.exe 拷出来、重新编译、再拿两份互相对比—— 于是旧的那个二进制加载的是新二进制编译出来的 shader。 改动恰好动了一个 C++/GLSL 双边镜像的结构体，旧二进制就按错误的 stride 去读 LOD 表，画出了不一样的几何。

破绽在这里：同一个二进制，在一轮里读 1.272 ms，在另一轮里读 1.406 ms。 基线会在两次测量之间漂移，那它就不是基线。

二进制配自己的 shader配对方的 shader
8 字节 MeshLod1.406 ms1.272 ms
16 字节 MeshLod1.407 ms1.689 ms

让每个二进制配自己的 shader 跑，所有配置都是 1.406 ms，那个 stride 根本不花钱。

确认它是假象的办法，是预测反方向：如果机制是我猜的那样， 那么拿新二进制去配旧 shader 也应该异常——结果是 +19.9%。对上了。

顺带一提，漂移门（drift gate）对这个完全无能为力：它只比较同一轮之内两次对照组的差异， 而这里两次对照组都一样地错。

07 / 收尾

留下了什么

一个被否决的特性，和一个我现在能直接回答的问题。如果有人问"你为什么没做 meshlet 剔除"， 答案不是"没来得及"，而是这张表、这个 7.7 倍、和那句 LOD 和 meshlet 锥体剔除在抢同一份收益。

我觉得这比做出来更有说服力一点。先量前提再写代码，最坏的情况是省下了一个 GPU pass 的工作量； 最好的情况是你学到了一件关于自己引擎的、原本不会注意到的事。

  • 已合入主干：buildMeshlets + meshletConeCulled（无 GPU 依赖，可单测）、--meshlet-analysis
  • 默认关闭：meshlet 构建本身（启动期开关）
  • 保持 8 字节：MeshLod——它是逐帧上传给 GPU 的，不该为一个不存在的特性带两个没人读的字段
