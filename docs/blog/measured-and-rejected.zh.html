三次否决，一次放行

四个看起来都该做的优化，都先量了再说。三个被数字劝退，而且是三种不同的死法； 第四个原本连"可测的对象"都没有，补上之后测出 −13.0%，于是做了。

Meshlet 锥体剔除
省下 0.055%

LOD 已经先拿走了同一份收益，效率是它的 7.7 倍。

Uber-shader 特化常量
+4.4%（更慢）

上限本身是负的——把特性代码整段删掉，主 pass 反而变慢。

并行命令录制

成本不在假设的地方；一个开关比十七个录制器的重构更划算。

深度预通道
−13.0%

同一套方法，这次说的是"做"。前提是先补上一个能测它的场景。

死法一 · 收益已被别人拿走

Meshlet 锥体剔除

设施做完了，GPU pass 没建——因为 LOD 先到一步。

先把 meshlet 建出来（落在现有索引缓冲里的连续区间，幸存者直接就是普通的 VkDrawIndexedIndirectCommand），然后在写 GPU pass 之前， 用 --meshlet-analysis 在六个场景上跑了 400 帧确定性回放， 先量"还剩多少可剔"。

唯一几何量有意义的场景：--scene stress
配置绘制三角形meshlet 数锥体剔除掉
LOD 按出厂设置190,3773,3230.055%
lod.forcedLod = 01,471,95617,90923.5%

两行差异就是全部答案。锥体剔除本身没问题——在稠密几何面前它能找到 23.5%。 但 LOD 选级和 meshlet 锥体剔除在抢同一份收益，而 LOD 先到： 它已经把 1,471,956 个三角形砍到 190,377（−87%），meshlet 再去找，只剩 0.055%。

LOD 在这套内容上的效率是 meshlet 剔除的 7.7 倍，代价是每个 draw item 一次 selectLodIndex，跑在一个本来就存在的 dispatch 里。

还有个更安静的原因：在这套内容实际选中的 LOD 级上，一整个球体只剩几个 meshlet， 每个 meshlet 都横跨物体大半，法锥宽到拒绝不了任何东西——meshopt 报的 cone_cutoff 直接是 1，也就是"永不拒绝"。 Meshlet 剔除想要的是"又大又密又近"的物体上的许多小簇，而 LOD 的全部工作就是保证这种物体永远不会被提交。

代价那一侧也记下来了：indirect command 数会 ×2.5。设施保留在主干、有单测、 默认关闭，所以将来换一套内容重测是一个命令行开关，不是一次重写。

死法二 · 上限是负的

Uber-shader 特化常量

先量了最好情况，发现最好情况比现状还慢。

simple_bindless.frag 有 1171 行，把虚拟阴影贴图、体积雾、 辐照度探针、cluster 网格全部无条件编进来，各自用运行时值开关——八个这样的分支， 而这些子系统默认全是关的。假设不是"分支本身贵"（在 IMR 上一个 uniform 分支很便宜），而是寄存器压力：编译器按最坏路径分配， 占用率一低，隐藏访存延迟的能力就变差。

关键在于没有先去实现特化常量，而是先测它的上限：把八个 gate 直接换成字面量 false，让驱动把分支体整段消除。这是一个公平的上界—— 特化常量能给驱动的就是这个，而且比运行时开关能给的更多。

测量条件
显卡时钟钉在 1100 MHz、显存 7001，全程无 throttle 原因触发。 重复的对照回到 0.72%（pass）和 0.87%（整帧），都在 1% 门槛内， 而效应是漂移的 6.1 倍。三对样本方向全部一致：+4.2% / +4.9% / +4.0%。 在第二个场景 fragment-stress 上佐证到 +4.3%，pass 的对照漂移 0.00%—— 但那组的整帧漂了 1.76%，所以它只作为方向与量级的佐证，不作为第二个过门禁的结果。

删掉本来就不执行的代码，让这个 pass 慢了 4.4%。所以要建的那套机器， 天花板在零以下。

顺带一个容易踩的坑：这里的 shader 由 glslc --target-env=vulkan1.3 编译，没有加 -O，所以死代码两种情况下都会被 glslc 原样发出， 消除全发生在驱动侧——SPIR-V 只缩了 0.8%，那点缩减算的是被删掉的分支指令而不是分支体。 SPIR-V 体积在这个问题上不是代理指标。 机制层面要继续追需要 VK_KHR_pipeline_executable_properties， 所以结论写的是"不要从源码重新推导"。

死法三 · 成本不在假设的地方

并行命令录制

量完之后，问题没变小，但解法换了一个——而且便宜得多。

"把录制拆到多线程"这个提案依赖一个当时没人有的数字。先补上仪表 （Record CPU 挨着已有的 Frame prep CPU， 外加一份逐单元的分解），答案的形状被改了两次。

第一次：录制确实值得动

RTX 3080 Ti Laptop，Release
场景GPU 帧prep CPUrecord CPU录制占 CPU
stress1.024 ms1.079 ms0.530 ms33%
default1.754 ms0.059 ms0.150 ms72%
fragment-stress2.149 ms0.089 ms0.182 ms67%

stress 是有意思的那一行：CPU 合计 1.6 ms 对上 1.0 ms 的 GPU 帧， 这个场景是 CPU-bound 的，而录制占了三分之一。另外两个舒舒服服地 GPU-bound， 在那里省 CPU 录制时间买不到任何东西。

第二次，也是决定性的：成本是集中的

逐单元分解显示，成本不是摊在十七个调度单元上的。 一个单元占了 63%，其余每个都在 0.015 ms 以下。 把十七个录制器拆成 primary/secondary 两半，等于去并行一个按构造就近乎串行的负载—— Amdahl 把录制这一侧的上限压在 1.6 倍 左右， 而代价是一次触及帧内每一个录制器的重构。

那个贵的单元是 punctual 阴影图集，它的成本是 CPU 侧的 caster cull， 而移除它的开关本来就存在。

一个设置开关，对上一次十七个录制器的重构，拿到的比线程化能给的还多。 录制保持单线程，真正交付的是那套让这个问题可回答的仪表。

对照 · 同一套方法说"做"

深度预通道

它一度不是"测了否决"，而是"没有可测的对象"。

深度预通道买的是"后来被覆盖掉的片元的着色"，所以它的价值是场景深度复杂度的函数。 而仓库里的场景要么深度复杂度约等于 1，要么是人为堆出来的六层、二十四层全屏板子—— 在后者上测，量的是"场景是怎么搭的"，不是内容。这个结论在文档里挂了几个月： 缺的是一个场景，不是一个 pass。

补上 Sponza 并加上一个过绘读数（pipeline statistics 计 fragment shader invocation） 之后，出来的数字把原来的场景清单整个推翻了：

专门用来制造过绘的两个场景，恰恰是整个仓库里有效过绘最低的。 堆叠的全屏四边形彼此完全遮挡，early-Z 在片元着色器之前就把绝大部分拒掉了。 几何层数是"场景是怎么搭的"的属性；invocation 才是硬件真正付的钱， 而预通道只能回收后者。

这四条合起来说明什么

三种死法是三种不同的东西：收益已经被别的机制拿走、 最好情况本身是负的、成本不在设计假设的位置上。 三次都不是"觉得不值得"，是量完之后数字不支持。

而第四条是同一套流程的另一个出口。它之所以有说服力，恰恰因为前三条存在： 一个只会说"做"的流程不是流程。

每一条被否决的结论都写进了 docs/design_decisions.md， 连同测量条件和"什么情况下结论会翻"——meshlet 那条明确写着 "在 Sponza 那种大块近处网格上会反转"，所以复测是一个命令行开关。
